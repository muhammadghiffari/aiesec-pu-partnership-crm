# Decisions, Constraints and Unresolved Source Questions

Date baseline: 28 October 2026. Changes require product-owner approval and an ADR if they affect a system invariant.

## Accepted decisions

| ID | Decision | Implementation effect |
|---|---|---|
| D-001 | Private repository target is `muhammadghiffari/aiesec-pu-partnership-crm` | Bootstrap is explicit and private; no public mirror |
| D-002 | Fixed EDGE_ANCHORED 13-page diagram is system-design baseline | Keep it in `docs/diagrams/`; PRD follows its domain structure |
| D-003 | Official lifecycle has five top-level stages only | Prospecting, Sales Process, Close Deal, Partnership Implementation, Post Survey |
| D-004 | Use ESSM industry categories and Project Support as classification | Legacy operational verticals are not canonical partner taxonomy |
| D-005 | Rate Card is structured and independently versioned | Catalog/package/item entities; proposals snapshot value calculations |
| D-006 | Merchandise Tracker is in scope | Dedicated merchandise entities and calculation tests |
| D-007 | TL BD and LCVP PD have identical CRM Lead permission profile | Organizational seniority does not imply different in-app permissions |
| D-008 | Both CRM Leads can assist staff work | They may work assigned/staff workflows as well as administration/review |
| D-009 | LoA submitter may never approve own LoA | Enforced in domain service and database constraint/trigger where feasible |
| D-010 | AI never sends or approves external communication/LoA | No send credentials/tools in worker; human approval/send is separate |
| D-011 | Official survey response contents are not integrated at first release | Link + dispatch/completion status only |
| D-012 | Real ESSM workbook/data is excluded from Git | Local authorized mapping/import process only |
| D-013 | Third developer is `hicesse`; Catalna continues as an existing developer | `hicesse` invited with write permission by bootstrap; do not guess Catalna's handle |
| D-014 | Developer model choices are separate from application runtime LLM | Runtime provider/model must pass independent access and evaluation checks |

| Q-27 | Who may approve outreach, and what "reviewed" means | BD staff and CRM Leads may approve outreach they drafted (PRD §11); viewers and anonymous callers cannot. Lint ERRORs block; WARNINGs are shown and counted in the audit record | Product owner |
| Q-28 | Lint rule set (PRD says "deterministic lint" without rules) | Version 1: length by channel, email subject rules, template placeholders, unverified-claim markers, internal negotiation notes, credential-like strings, insecure/shortened links, hidden/bidi control characters, guarantee promises (errors); salutation at the start, closing, capitals, exclamation marks (warnings). | Q-29 | What "send" means in the CRM while sending is manual | `confirmSent` records that a human sent the approved text through the approved sender profile; it never sends. Follow-up scheduling and the three-follow-up ceiling are M2-05 | Product owner |
| Q-30 | How a catalog price change is made without altering history (PRD: "versioned", "historic proposals must not change") | Edits happen only in a DRAFT version (one per catalog name), copied from the latest version with all values reset to PROPOSED. Activating freezes it and retires the previous ACTIVE version in the same transaction, ending its window the day before the new start. ACTIVE/RETIRED rows are immutable in the application and by database trigger. The new version must start after the one it replaces | Product owner |
| Q-31 | When a value counts as "confirmed" (PRD: initial values are unconfirmed until verified; never present examples as official national prices) | Every value starts PROPOSED. A CRM Lead marks it CONFIRMED (recorded with who and when); editing a confirmed value voids the confirmation. Activating a version with unconfirmed active items needs `acknowledgeUnconfirmed: true` and the count is audited. Seed values must come from an approved source (M1-02 style seed), not from this code | Product owner / ESSM standard owner |
| Q-32 | `ratecard.edit` and `package.edit` permissions | Both are CRM Lead only (PRD §11, already in `policy.ts`). Packages are edited through `package.edit`, items/versions/activation through `ratecard.edit`. Reading uses `ratecard.read`, open to viewers | Product owner |
| Q-33 | Rounding and money rules for proposal totals (M3-02 asks for "rounding/IDR integer rules"; none are written down) | Whole rupiah only. Quantity has at most 3 decimals. Line total = round half up of quantity x agreed unit value, computed in integers (`((qty*1000)*unit + 500)/1000`), identical in TypeScript and as a database CHECK. Rounding happens per line, then lines are summed. Values above 1e12 per unit or products above 2^53 are refused, not rounded | Product owner / treasurer |
| Q-34 | How a package and extra benefits combine in a proposal (PRD: "no package/benefit double counting") | PACKAGE proposal = the package's listed price; its benefit lines are shown for the delivery obligation but are inside that price and never added. HYBRID = package price + custom lines; a custom line for a benefit the package includes is refused. CUSTOM = sum of custom lines. A benefit appears once per proposal | Product owner |
| Q-35 | Negotiated prices (the diagram has both catalog and agreed values) | Each line keeps the catalog unit value and the agreed unit value; the difference is visible. Any agreed value >= 0 is allowed; no discount ceiling or approval is implied (PRD §4: "no fixed deal approval threshold") | Product owner |
| Q-36 | Which catalog version a new proposal uses | The ACTIVE version whose window covers today (Asia/Jakarta). If none covers today, creation is refused; a retired version is never revived for new proposals. All lines of one proposal come from one version | Product owner |

## Superseded assumptions

- PRD v1.1 said merchandise tracking was out of scope; replaced by D-006.
- PRD v1.1 used eight “verticals” as target taxonomy; replaced by D-004.
- PRD v1.1 defined TL BD as a separate `super_admin` permission role while LCVP PD had different capabilities; replaced by D-007/D-008. A deployment or technical administrator flag may exist only as an infrastructure concern and must not create business-permission disparity between CRM Leads.
- Earlier examples that embedded tactics (e.g. specific outreach tactics or time windows) are operating guidance and are not CRM stages or schema enums.
